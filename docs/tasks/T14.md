# T14 — Expiry scheduler, lag metrics, and alerts

| Field | Value |
|---|---|
| Phase / week | Starts in Phase 5 / Week 6 (~8 hours scheduler and lag tests); completed in Phase 6 / Week 7 (~8 hours monitoring dashboards and alerts) |
| Depends on | Expire use case (T11), T13 messaging pipeline for Outbox lag; observability stack in week 7 |
| Blocks | T15 (release readiness expects monitoring), week-6/7 exits |

## Context

The scheduler must release expired reservations even when RabbitMQ is down. Week 6 must not rebuild expiry logic (skeleton and testable clock come from week 4). Week 7 completes dashboards and a test alert. The alert **channel** is an OPEN DECISION; a local test receiver is enough in a practice environment.

## Exact scope

### Week 6 (required for week-6 exit)

- `scheduler` service, same backend image, **one** instance. Every minute, limited batches, same expire use case, tenant-scoped transactions from an operational list of active orgs. Locks neutralize accidental concurrency.
- Independent of the notification queue.
- Metrics/heartbeats from scheduler (and hooks for Outbox lag, even if Grafana is week 7): age of oldest unpublished Outbox; expired-but-unreleased reservations (threshold starting value: still held >2 minutes after expiry).
- Test: scheduler releases stock without RabbitMQ running.

### Week 7 (required for week-7 exit)

- Profile `observability`: `prometheus`, `grafana`, `ops-exporter` (read-only metrics: Outbox lag, scheduler, final job failures, backup freshness hook if available).
- JSON logs already should include time, level, service, request id, trace id, optional tenant/business refs. OTel traces + `traceparent`; no high-cardinality Prometheus labels (no order/user/org ids).
- Initial alert thresholds from `AGENTS.md` §21 (5xx >1% in 5 minutes, Outbox age >60s, queue growth or new final failure, unreleased expiry >2 minutes, connections ~80%, disk 80/90%, backup older than 14 hours, any stock-balance mismatch). These are starting values to tune after a week of data (OPEN DECISION on final numbers and channel).
- Prove a test alert is received on the chosen (possibly local) receiver.
- Runbooks: queue outage, worker stop, DB slowness, lost secret, data corruption.

## Tests required

- Heartbeat / oldest-work age is exposed
- (Week 7) alerting rule fires in a test condition

## Out of scope
