## Context

The product database and the Keycloak database must be separate, with separate users. Schema changes run as a dedicated owner role through the `migrate` job. The API uses a limited runtime role. This task makes `postgres` and `migrate` real, and makes `/health/ready` check connectivity and schema version.

## Exact scope

1. PostgreSQL **17** service in Compose, with a persistent volume. Init scripts under `infra/postgres/` that create:
   - Logical databases `stockpilot` and `keycloak`
   - Separate passwords/users for each (values from secrets or env files, not committed)
   - In `stockpilot`: a **migration / schema-owner** role and a **runtime** role (login, no superuser, no `BYPASSRLS`, not owner of application tables after grants)
2. Alembic with **one** branch. First migration should:
   - Create schemas `access`, `catalog`, `sales`, `inventory`, `notifications`, `platform`
   - Install any required extensions (only if needed, e.g. for UUID; do not add unused extensions)
   - Grant runtime-role usage on schemas (table grants will grow in later migrations)
   - Optionally a small `platform.schema_migrations` visibility path or use Alembic’s version table so `/health/ready` can confirm the expected revision
3. `migrate` Compose service: one-shot, uses the backend image, runs Alembic as the migration role, `service_completed_successfully` for dependents.
4. API runtime config points at the runtime role only. `/health/ready` succeeds only when Postgres is reachable and the schema revision is the expected one.
5. Document role purpose in `docs/architecture/` or the ADR index (full RLS policies are T06; mention that the runtime role is prepared for RLS).

Do **not** create all business tables in the first migration. Tables arrive with the tasks that own them (T05–T11). Creating empty schemas now prevents later migrations from fighting over schema creation.

## Files to create or touch

- `infra/postgres/` init SQL or init scripts
- `backend/alembic/` (env, versions, `alembic.ini` if used)
- First revision under `backend/alembic/versions/`
- `compose.yaml` / `compose.dev.yaml`: `postgres` healthcheck, `migrate` service, env/secret wiring
- `.env.example` placeholders for DB names and users (no real passwords)
- API settings and `/health/ready`
- README quickstart: up postgres → run migrate → up api
- Optional `docs/architecture/database-roles.md`

## Step-by-step implementation notes

1. Use the official Postgres 17 image; pin digest after a successful pull/test (`versions.md`).
2. Init scripts must be idempotent enough for a fresh volume. Document that re-running against a dirty volume is not the migrate path.
3. Alembic `env.py` must not put business rules in migrations. Use the migration role URL, not the runtime URL.
4. Never log passwords. Compose secrets: only the services that need them.
5. Keycloak is not started in this task, but the `keycloak` database and a dedicated DB user should already exist so T05 does not redesign init.
6. `/health/live` stays independent of Postgres (process liveness). Readiness is the place for DB/schema checks. Do not include RabbitMQ in readiness.
7. On Windows, if host port `5432` is already taken (a local Postgres install is a common cause), publish a different host port in Compose and keep container port `5432`. Document the override in the README. Quickstart commands stay PowerShell, one per line.
7. Add a Compose test or a check in `backend-checks` (may land in T04) that migrate applies cleanly on an empty database.

## Acceptance criteria (week-1 exit)

- From a fresh volume, `docker compose … up -d --wait postgres` then `run --rm migrate` applies the first revision.
- API `/health/ready` becomes successful after migrate.
- Two databases exist; migration role and runtime role are distinct; the API cannot be configured (in the default compose) to connect as the schema owner.
- No business-table sprawl in the first revision.

## Tests required

- An integration or check job that starts Postgres 17 (Compose) and applies migrations on an empty database. This can be wired in T04’s `backend-checks` if T04 immediately follows; T03 should at least leave a command that proves migrate works.
- No SQLite.

## Out of scope

RLS policies, Keycloak containers, Outbox tables (T11), product/order tables, CI workflow (T04, unless you only prepare the migrate step).
