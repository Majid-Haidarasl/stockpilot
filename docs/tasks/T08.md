## Context

Week-3 exit: receipts and adjustments work, and the movement ledger is visible. Reservations’ competitive tests are T09, but the position model and invariant must already be in place.

## Exact scope

- `inventory.stock_positions`: one row per `(organization, warehouse, product)` (v1: one warehouse per org). Check constraint `0 <= reserved <= on_hand`. Max `on_hand` 1,000,000,000.
- Position is created on **first receipt**; uniqueness controls concurrent creation. Reserve on a missing position = zero stock (implemented in T09); do not pre-create rows on reserve.
- `inventory.movements`: append-only ledger with physical delta, reserved delta, reason, reference, and user.
- APIs: `GET .../inventory` (on_hand, reserved, available=`on_hand-reserved`); `POST .../inventory/receipts` (positive qty + reference); `POST .../inventory/adjustments` (signed qty, **required reason**). Decreasing adjustment must not take `on_hand` below `reserved`. Actor and reason required.
- Permissions: `warehouse` and `admin` write; `viewer`/`sales` cannot adjust (sales has no inventory correction). `viewer` denied even via direct API (scenario 11 — API part here; UI message may complete in T12).
- Minimal UI: inventory list and ledger visibility (week 3 includes ~4 hours for display).
- Ops balance-check command may start here (sum of movements vs counters); full reserved-vs-reservations check completes with T09/T11. Silent auto-repair is forbidden.
- Lock only the relevant position on adjustments; do not lock orders.

## Step-by-step implementation notes

1. Integer quantities only. Reject receipts/adjustments that would exceed caps.
2. Ledger is the source for balance explanation; counters on the position are the operational truth, checked against the ledger.
3. Use `SELECT ... FOR UPDATE` on the position. Isolation `READ COMMITTED`.
4. Domain tests: invariant, decreasing adjustment blocked, no negatives.

## Acceptance criteria

- Receipt and adjustment work; ledger is visible (week-3 exit, together with T09 for competitive reserve).
- available is computed, not independently edited.

## Tests required

- Domain invariant tests
- Adjustment below reserved rejected
- Concurrent first-receipt creation does not produce two positions
- Permission: viewer cannot adjust via API
- Ledger sums match counters after a sequence of receipts/adjustments
