## Context

Two independent organizations must work, and changing tenant or order ids in a request must not grant new access (acceptance scenario 1). This task implements membership, the permission matrix, `ActorContext`, repository tenant filters, composite-ready schema, and RLS.

## Exact scope

- Tables `access.tenants`, `access.memberships` with unique `(user, organization)` and external identity `(issuer, subject)`.
- One role per membership: `admin`, `sales`, `warehouse`, `viewer`. Permission checks on every commercial request. Last active admin cannot remove their own admin role; use an organization lock against a concurrent last-admin removal (critical test).
- Build immutable `ActorContext` from the session and membership, never from a free-form body. Path parameter `tenant_id` is the selected org and must match membership.
- Cross-tenant resource: `404`. Same-tenant missing permission: `403`.
- Enable RLS on commercial/tenant-scoped tables as they exist (and on tenants/memberships as designed). Runtime role is not owner, not superuser, not `BYPASSRLS`. `SET LOCAL` tenant context only inside the current transaction. Isolation tests run as the **runtime** role.
- Auth and “list my organizations” work **before** a tenant is selected.
- `ops bootstrap` (audited, idempotent) creates organizations and links existing Keycloak users; operator-only in production-like settings. Week-2 demonstration depends on this tool (plan did not pin the week; PM placed it here).
- Frontend: organization picker; after switch, clear tenant-sensitive cache (query keys will include `tenant_id` once data pages exist).
- Complete `ADR-003`.

## Step-by-step implementation notes

1. Do not let the API use the schema-owner role in tests that claim RLS works.
2. Composite FKs including `tenant_id` start with whatever tenant-scoped tables exist; later modules must follow the same pattern.
3. Add the critical test: concurrent attempt to remove the last admin.
4. Cross-tenant GET/PATCH with a real session of org A against org B ids returns 404.

## Acceptance criteria

- Two independent organizations; users see only their org; tampering with ids does not leak data (scenario 1).
- Unauthorized / wrong-role actions are rejected.
- RLS tests pass as the runtime role.
- Last-admin invariant holds under concurrency.

## Tests required

- Two-org isolation (API)
- Permission matrix samples for each role
- Concurrent last-admin removal
- RLS tests with runtime role (not table owner)

## Out of scope

Product/customer CRUD (T07), inventory, orders. Do not add a public invite-by-email flow.
