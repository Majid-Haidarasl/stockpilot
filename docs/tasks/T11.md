## Context

Week-4 exit: draft, reserve, confirm, cancel, expire, and ship work from the API, with transactions and critical tests. This is a control-point week: if reserve and cancel are not correct, stop adding features.

## Exact scope

- One PostgreSQL transaction for reserve, confirm, cancel, expire, and ship: order change + inventory change + audit + **Outbox row** + idempotency response. Rollback on any required failure.
- `UnitOfWork` in the use case; inventory adapter stages only; no inner `commit`. Lock order: idempotency record, order, products (stable id), positions (stable id), reservation.
- Endpoints: `POST .../orders/{id}/reserve|confirm|cancel|ship`. Reserve returns expiry. Confirm of an expired reservation expires, releases stock, records, returns `409` `RESERVATION_EXPIRED` **without** rolling back expiry.
- Inventory effects exactly as the table in `AGENTS.md`. Cancel of `DRAFT` releases nothing. Second cancel must not increase stock (even with a new idempotency key). Ship only from `CONFIRMED`; consume once (`CONSUMED`). Confirmed orders do not auto-expire.
- At reserve: read price and active flag under product lock; freeze snapshot; all-or-nothing; `INSUFFICIENT_STOCK` with per-SKU requested/available; no commercial writes on failure (deterministic 409 may be stored as idempotent response).
- `Idempotency-Key` on all commercial mutating commands; scope `(org, user, operation)`; fingerprint of method, path, contract version, canonical body; `IDEMPOTENCY_KEY_REUSED` on body mismatch; store final HTTP status/body/headers in the same transaction; do not store 500/transient errors; keep ≥72 hours; concurrent same key waits, then `Retry-After`.
- `expected_version` / `version` and `VERSION_CONFLICT`.
- Outbox **table and writer** for events such as `OrderReserved.v1` (minimal payload, tenant_id, tracing context). Relay process is T13. Keep design in `ADR-005` as accepted-in-principle.
- Expire use case callable from a future scheduler and from confirm; no public expire route.

## Step-by-step implementation notes

Follow the reserve path in `AGENTS.md` §9 (validate session/membership/key → UoW → idempotency lock → short-circuit prior response with current permission still checked → lock order → product locks → position locks → reserve or reject → movements, audit, Outbox → store response → commit → return without waiting for notifications).

## Acceptance criteria

- Week-4 exit: all cycle commands work from the API with transactions and critical tests.
- Scenarios 2–9: no stock on draft; successful reserve reduces available and freezes price; one short line reserves nothing; concurrent reserves cannot go negative; same key does not create a new effect; cancel releases exactly once; confirm after expiry is forbidden (and expiry is recorded); only confirmed orders ship.
- API reserve is `200` with the order view, not `202`.

## Tests required (non-removable for this domain)

- Concurrent last-stock reserve
- Multi-line shortfall
- Idempotent replay
- Second cancel
- Expire vs confirm race
- Cancel vs ship race
- Price change during reserve
- Cross-tenant order request
- Rollback of order+stock if movement or Outbox write fails
- Confirm-after-expiry commits expiry and returns 409
