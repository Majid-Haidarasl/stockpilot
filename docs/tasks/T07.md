# T07 — Catalog and customers with tenant boundaries and a minimal UI

| Field | Value |
|---|---|
| Phase / week | Phase 2 / Week 2 (~8 hours) |
| Depends on | T06 |
| Blocks | T08 (inventory needs products), T10 (orders need customers and products) |

## Context

Week-2 exit also requires creating and viewing a product of the same organization from the UI. Catalog and customers stay simple; do not over-pattern them.

## Exact scope

- `catalog.products`: unique `(tenant_id, sku)`; title, integer `IRR` price, active flag, version, non-negative stock warning threshold (set by `admin`). Cannot delete a product used on an order (when orders exist; until then, still no casual hard-delete without a deactivation path).
- `sales.customers`: name and minimal contact details, tenant-scoped.
- APIs: `GET/POST /api/v1/tenants/{tenant_id}/products`, `PATCH .../products/{id}` with version + audit; `GET/POST .../customers` and `PATCH` for edit. Permissions: follow the matrix (`sales` manages customers; catalog management is for authorized users — `admin` has all rights; do not grant `viewer` writes; `warehouse` must not change prices).
- Price stored as 64-bit integer; JSON money string + `"IRR"`. Caps: unit price ≤ `10^12`.
- Minimal Persian UI: product list/form and customer list/form, tenant-keyed queries, loading/empty/error states.
- Audit log rows for sensitive product/customer changes (`platform.audit_log` may be introduced here if not already).
- Composite FKs with `tenant_id` and RLS policies in the same pattern as T06.

## Files to create or touch

- Alembic migrations for `catalog.products`, `sales.customers`, grants, RLS, FKs
- `catalog` and `sales` (customer only) modules + `public.py` (catalog public contract used later to freeze prices)
- Frontend feature pages
- Contract/integration tests for tenant isolation on SKU uniqueness (same SKU allowed in two orgs)

## Step-by-step implementation notes

1. Two orgs may both use `SKU-100`.
2. Product title/price changes must not be designed in a way that later rewrites reserved order snapshots (those snapshots appear in T10/T11).
3. Deactivating a product will later block new reserves only (document the invariant now).
4. Keep modules slimmer than `sales`/`inventory` order core.

## Acceptance criteria

- Same-org product create and view work from the UI (week-2 exit).
- Cross-org access returns 404; unauthorized writes rejected (scenario 11 will later also cover inventory).
- SKU uniqueness is per tenant.

## Tests required

- Tenant isolation for products and customers
- Version conflict on product PATCH
- Permission checks (e.g. viewer cannot create a product; warehouse cannot change price)
- Domain tests for money/price caps as applicable

## Out of scope

Stock positions, orders, dashboard, Playwright main path.
