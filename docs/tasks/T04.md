## Context

Week-1 exit requires domain tests and import-boundary checks to pass in CI. From the first week, every change should be mechanically checkable inside containers, including GitHub Actions.

## Exact scope

1. **Ruff** for format and lint (no second Python formatter/linter).
2. **mypy** on the backend, configured for the package.
3. **Import Linter** contracts that fail when:
   - `domain` imports `sqlalchemy`, FastAPI, Celery, or HTTP models
   - `application` imports a database adapter
   - one module imports another module’s internal repository (only `public.py` / public contracts are allowed)
4. **ESLint** and TypeScript check (and Vitest harness if the shell can host a trivial test) for the frontend.
5. A **sample domain unit test** that does not need the network or database — for example `Money` addition in `IRR`, refusal to add different currencies, or a tiny quantity invariant. If `Money` is not yet used in production code, implement the minimal value object in `domain` (shared carefully: money is a domain concept; do not park it in `platform` as a business rule). This proves the unit-test path.
6. Compose services, profile `test`:
   - `backend-checks` — one-shot: Ruff, mypy, Import Linter, pytest for unit/architecture (and migrate-on-empty-Postgres if T03 is done)
   - `frontend-checks` — one-shot: ESLint, `tsc`, unit tests
7. **GitHub Actions** workflow: checkout, run the same Compose check services (or the equivalent documented container flow). Permissions default to read. No deployment secrets. Third-party actions pinned by version or digest (**pin after lookup; do not invent SHA values if you have not recorded them** — if needed, leave a clearly marked TODO in `versions.md` rather than a fake hash).
8. README documents:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile test run --rm backend-checks
docker compose -f compose.yaml -f compose.dev.yaml --profile test run --rm frontend-checks
```

## Step-by-step implementation notes

1. Install quality tools as locked dev dependencies via uv/npm **inside Docker**, update lockfiles.
2. Keep the sample domain test fast and meaningful (a real rule, not `assert 1 == 1`).
3. Architecture tests should demonstrate a **failing** case in comments or a fixture that would be illegal, and a passing current tree.
4. `backend-checks` may need `postgres` if you include “migrate empty DB”. If so, use `service_healthy` and the same Postgres 17 image, never SQLite.
5. CI must not require Python/Node on the runner host beyond Docker-in-Docker or the platform’s documented Compose path. Prefer building/running the project’s own check images.
6. Do not yet fail CI on coverage 85% for an almost-empty domain. Record the coverage target in docs; enforce it when domain code exists (Phase 3).
7. Document the official check commands in PowerShell in the README (one command per line; no bash `&&`). CI still runs Linux containers on GitHub-hosted runners — that is not a Windows-container change.
8. pip-audit, Gitleaks, and Trivy are **not** required to block week 1 (the plan attaches them to the release line; the PM placed them in week 7 — OPEN DECISION on exact week, see `AGENTS.md` §27 item 11). You may add a non-blocking job later; do not expand Phase 1 to a full security program.

## Acceptance criteria (week-1 exit, together with T01–T03)

- From a fresh clone: API and sample UI start; first migration runs; domain test and import checks pass locally via Compose and in GitHub Actions.
- `backend-checks` and `frontend-checks` are the official commands; README has no hidden host steps and is PowerShell-safe.
- Import Linter would catch a domain-layer SQLAlchemy import (prove with a documented or automated test).

## Tests required

- Sample domain unit test (e.g. `Money`)
- Import/architecture contracts
- CI green on the default branch / PR simulation
- Optional: migrate-on-empty-database check

## Out of scope

Playwright e2e, Locust, Keycloak, business reservation tests, release image publishing to GHCR (can be a later workflow). Do not implement the order aggregate here just to inflate coverage.
