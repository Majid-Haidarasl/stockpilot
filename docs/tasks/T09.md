## Context

The product’s first concrete problem is oversell under concurrency. This task completes `InventoryCommands` (`reserve_all` and the related allocate/release/consume operations as ports, even if sales wiring is T11) and proves races on **real PostgreSQL 17** with independent connections.

## Exact scope

- Public inventory port: `reserve_all` (and typed commands for release, allocate, consume as needed). Returns reservation id. **No commit** inside the adapter. Stages reservation rows (`inventory.reservations`, `reservation_lines`), updates counters, writes movements, all in the caller’s unit of work.
- All-or-nothing: if any line is short, no line is reserved; no commercial writes persist; the outcome lists SKU, requested, available (for later `INSUFFICIENT_STOCK`).
- One reservation per `(tenant, order)` in v1; max 20 lines; no duplicate products; missing position = zero available.
- Lock order for inventory-side work when called from a use case: products in stable id order, then positions in stable id order, then reservation (the outer use case also locks idempotency and the order first — document the full sequence and obey relative order).
- Reservation starts `HELD` with `expires_at` (30 minutes) when used by reserve; allocate/release/consume implementations should exist so T11 does not invent counter math.
- Critical concurrency test: two connections reserve the last stock (e.g. 10 on hand, two reserves of 7) — only one succeeds; `available` never goes negative.
- Hypothesis sequences of receipt, reserve, release, ship/consume: non-negativity and balance.
- Complete direction of `ADR-002` if the shared UoW appears here; T11 will use it end-to-end.

## Files to create or touch

## Step-by-step implementation notes

1. Never use SQLite. Use two real connections, start together.
2. After `FOR UPDATE`, re-read stock.
3. Retry whole use case ≤3 times on deadlock with short random backoff; no external I/O in the transaction.
4. Deactivated product: block new reserve (need catalog public read of active flag under product lock — if catalog lock is only in T11, at least accept product status in the command or port).

## Acceptance criteria

- Competitive reserve on a real database cannot oversell (week-3 exit with T08).
- Multi-line shortfall reserves nothing (critical test).

## Tests required

- Concurrent last-stock reserve (non-removable)
- Multi-line reserve with one short line (non-removable)
- Balance of HELD reservations vs `reserved` counters
- Deadlock retry does not double-apply (if reasonably testable)

## Out of scope

HTTP order API (T11), frontend, Outbox publishing, scheduler process.
